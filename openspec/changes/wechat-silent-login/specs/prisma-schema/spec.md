## ADDED Requirements

### Requirement: User model carries WeChat identity fields
The `User` model in `prisma/schema.prisma` SHALL include WeChat identity columns so silent login can identify and persist users: `openid` (unique `String`), `unionid` (nullable `String`), `session_key` (nullable `String`), and `last_login_at` (nullable `DateTime`). These are additive and MUST NOT alter the existing 13-table structure or other columns.

#### Scenario: openid is unique per WeChat user
- **WHEN** a migration is generated from the updated schema
- **THEN** the `user` table has a unique index on `openid` and two distinct WeChat users cannot share the same `openid`.

#### Scenario: New WeChat fields are nullable-safe
- **WHEN** the schema is validated with `prisma validate`
- **THEN** `unionid`, `session_key`, and `last_login_at` are optional (nullable) and existing rows remain valid without these values.

### Requirement: planet_code generation for silent-login users
The system SHALL guarantee that a `user` created during silent login receives a unique, non-empty `planet_code` (since `planet_code` has no database default and is `@unique`), generated by the backend login service at the moment of first creation.

The `planet_code` SHALL be a 6-character id generated from the alphanumeric character set `A-Za-z0-9`, with the **first character MUST be an uppercase letter (A-Z)** and the remaining 5 characters drawn from the full alphanumeric set (`A-Z`, `a-z`, `0-9`). The system SHALL ensure the generated `planet_code` does not collide with any existing `planet_code`; if a collision is detected (duplicate), the system SHALL regenerate a new `planet_code` and retry until a unique one is obtained.

#### Scenario: Newly created user has a planet_code
- **WHEN** a silent login creates a new `user` record
- **THEN** the record's `planet_code` is populated with a unique value that does not collide with existing `planet_code` values.

#### Scenario: planet_code format is a 6-char id with leading uppercase letter
- **WHEN** a silent login generates a `planet_code`
- **THEN** the value is exactly 6 characters long, the first character is an uppercase letter `A-Z`, and the remaining 5 characters are each one of `A-Za-z0-9`.

#### Scenario: planet_code collision triggers regeneration
- **WHEN** the generated `planet_code` already exists for another user
- **THEN** the system regenerates a new `planet_code` and retries until a unique, non-colliding value is persisted.
